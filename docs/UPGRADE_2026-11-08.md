# Upgrade 2026-11-08 — profile fields, activity types, activity linking

Three **additive** migrations. Nothing is dropped, renamed, truncated or rewritten:
every new column is nullable and existing rows keep their values.

## 1. Back up first (mandatory on the production server)

```powershell
powershell -ExecutionPolicy Bypass -File scripts\backup-database.ps1
```

Keep the resulting `.sql.zip` until the new version has run for a few days
(`docs/BACKUP_RESTORE.md` explains the restore).

## 2. Apply

```bash
php artisan migrate --pretend   # optional: prints the SQL without running it
php artisan migrate
```

| Migration | Effect on existing data |
|---|---|
| `2026_11_08_000001_add_profile_fields_to_prospects_table` | Adds nullable `business_activity`, `source`, `source_other`, `previous_software` and indexes on `contact_person` and `source`. Existing prospects get `NULL`. |
| `2026_11_08_000002_add_activity_type_to_follow_up_tasks_table` | Adds nullable `follow_up_tasks.activity_type` (`call` / `appointment` / `message`). Existing follow-ups get `NULL` (shown as "type not set"; the user picks one when editing, or when completing). |
| `2026_11_08_000003_add_linking_to_activities_table` | `activities.prospect_id` becomes **nullable** (native activities can exist before being linked). Adds `title`, `linked_at` and `follow_up_task_id` (nullable, UNIQUE, foreign key to `follow_up_tasks`, restrict on delete). Existing activities keep their prospect; `title` / `linked_at` / `follow_up_task_id` are `NULL`. |

Rollback (`php artisan migrate:rollback --step=3`) removes the new columns. The
last migration refuses to roll back while unlinked activities exist (link them
first), so a rollback can never delete activity history.

## 3. Behaviour that clients must know

* Activity type `appointment` is new. Existing rows keep `meeting`, which means the same thing:
  filtering by `appointment` returns both, and clients label both "Appointment".
* `POST /follow-ups/{id}/complete` with `create_activity: true` creates the activity in the same
  transaction; `activities.follow_up_task_id` is unique, so a follow-up can never produce two
  activities, and completing twice is refused (`INVALID_FOLLOW_UP_STATE`).
* `POST /activities` creates an activity on its own; `POST /activities/{id}/link-prospect` links the
  existing row (no copy). Moving an already linked activity requires `confirm_relink: true`
  (`409 ACTIVITY_ALREADY_LINKED` otherwise); activities that came from a follow-up cannot be moved.
* Prospect search (`GET /prospects?search=`) also matches the prospect id and phone numbers
  regardless of spaces / dashes, and never depends on the stage.

Full request / response formats: `docs/API.md` (sections 3.4, 3.6, 3.7, 6, 8, 9).
